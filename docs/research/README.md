# Investigación compartida — EspacioKoop Office

Biblioteca de referencias para **Varo, Eloy y sus agentes**. Su objetivo es aprovechar ingeniería existente al construir nuestra app/juego/gestor colaborativo: oficina, tareas reales, interacción, aprendizaje comprobable, progresión e historia.

**Estado: investigación y propuestas. No es una selección de stack acordada ni una aplicación implementada.** No se han instalado estos proyectos, conectado agentes, reproducido benchmarks ni probado interoperabilidad bilateral durante esta investigación.

## Cómo se ha organizado la búsqueda

Varo encargó una búsqueda multiagente por Internet. Se separaron tres frentes de investigación pública:

1. Oficina y mundo visual: renderizado, escenas, presencia y sincronización.
2. Coordinación y trabajo real: procedimientos, entregables, delegación y contratos entre agentes existentes.
3. Conocimiento, gamificación e historia: procedencia, habilidades, recompensas y crónicas navegables.

ARQUÍMEDES consolida como único escritor, elimina duplicados, contrasta fuentes y distingue los hallazgos de cada frente de la recomendación final. La revisión documental posterior no es una prueba de ejecución de los upstream.

## Criterio de selección

- Preferir componentes que cubran un requisito concreto; no coleccionar frameworks por popularidad.
- Comparar **reutilizar, adaptar, sustituir o estudiar como patrón**, justificando la elección. No dar por mejor una reescritura.
- Diferenciar aplicación completa, biblioteca, protocolo y referencia de investigación/diseño.
- Comprobar README y, cuando se indique, archivos concretos de implementación. Una funcionalidad documentada no demuestra uso real en nuestro entorno.
- Prioridades del catálogo: **P1** estudiar primero, **P2** alternativa o subsistema posterior, **P3** referencia condicionada. No son compromisos de implementación.
- Separar coste técnico, dependencia operativa y restricciones de licencia; no confundir que algo sea público con permiso para copiarlo.

## Reglas para la futura reutilización

Antes de incorporar código o assets, registrar fuente, revisión, componente, licencia, avisos/NOTICE aplicables, modificaciones, uso y estrategia de actualización. Este catálogo **no incorpora código ni assets de terceros**.

La licencia detectada por la API de GitHub es orientativa: comprobar el archivo aplicable al componente. Código, documentación y recursos gráficos pueden usar condiciones distintas. No interpretar `NOASSERTION`, ausencia de LICENSE o una licencia del paper como autorización del motor.

Mantener la separación entre:

- **Hechos:** tareas, resultados, evidencias y eventos autorizados.
- **Conocimiento validado:** procedimientos con procedencia, revisión, versiones y revocación.
- **Representación y ficción:** animaciones, humor, biografías narradas y leyendas, sin cerrar tareas ni conceder permisos.

La memoria compartida no concede autorización. Filtrar antes de recuperar contexto; probar revocación durante una tarea y propagación de correcciones a resúmenes, premios y cachés. Un editor visual de grafos no equivale a asignar trabajo real al arrastrar un personaje. Un adaptador LLM no integra por sí solo los agentes existentes de ambos propietarios.

## Próxima decisión conjunta

Elegir candidatos por componente, alojamiento/acceso privado, autoridad sobre tareas e interfaces disponibles de ambos lados. Las propuestas de Curro y Odiseo sobre una primera entrega más pequeña están en el debate; **este catálogo no las convierte en acuerdo**. Mantener la visión completa al fijar una secuencia de entregas verificables.
